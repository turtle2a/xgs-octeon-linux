- Driver bug found and fixed (Task 9 item 7, real hardware-offloaded TCP transit): the microflow idle timeout sent to firmware was the hardcoded constant `OCTEP_FT_TIMEOUT=244141`. The firmware's `mflow_timeout` field is documented and measured (reference project) in seconds of idle time before expiry; 244141 seconds is about 2.8 days, far outside any sane range, and firmware was silently clamping/rejecting it and self-invalidating the microflow (`state` 2->0, `fw_valid` 1->0) within 1-2s of creation regardless of traffic. New module param `ft_mflow_timeout` (int, default 60, matching the reference project's confirmed-working value) replaces the constant at both call sites in `octep_ft_program_locked()`. Builds with `W=1`, no warnings. Test spec: deploy, `cat /sys/module/octep/parameters/ft_mflow_timeout` reads `60`; run `octep-hook-live.sh "" "" 420` with a concurrent iperf3 and the `rpc_mflow_read` live-readback loop already in the hook script. Pass: a created microflow holds `state=2 fw_valid=1` for multiple seconds of real elapsed time (not collapsing within 1-2s) and the `WIRE_TO_WIRE` NPU counter rises above 0. Fail: `state` collapses to 0 within 1-2s regardless of the param value. Result (hook run 44, 420s window): PASS — flow held `state=2`/`fw_valid=1` for about 75-90s with `WIRE_TO_WIRE` counting genuine hardware-forwarded packets for the first time, then still collapsed to `state=0` under continuous traffic (see next entry).

- Second, deeper firmware bug found (same item 7): even with a sane 60s timeout, a microflow still expires (`state` 2->0, `fw_valid` 1->0) after about 75-90s of continuous, active iperf3 traffic through it (confirmed both via the NPU counters and the iperf3 client itself showing `0.00 bits/sec`/`Retr` at the same moment). The reference project's own `octep_flow_keepalive()` only *reads* a microflow's internal timestamp (to drive the host's own pf connection-tracking state) and explicitly never re-arms firmware's own idle timer, on the design assumption that a genuinely busy flow's timer is refreshed internally by firmware without host involvement; that assumption does not hold on this firmware. Since this is firmware-side and not something we can fix directly, added a host-side proactive workaround: new module param `ft_mflow_rearm` (int, default 20 seconds, 0 disables) and a new `octep_ft_rearm_locked()` function, called once per second from the existing `octep_ft_work()` delayed-work handler alongside the existing `octep_ft_scan_locked()`. For every live connection slot, if more than `ft_mflow_rearm` seconds have passed since its last re-arm, both directions are re-programmed by re-issuing `MFLOW_PROGRAM` (the same RPC+payload pattern `octep_ft_teardown_locked()` already uses for clearing, via `octep_ft_fill_mflow()` + `octep_rpc_flow_write_locked()`), well inside the 60s firmware timeout (3x safety margin). Worst case RPC load: `OCTEP_FT_CONNS=8` connections x 2 directions = 16 extra writes per 20s, negligible next to existing per-second scan/create traffic. Builds with `W=1`, no warnings. Test spec: deploy, `cat /sys/module/octep/parameters/ft_mflow_rearm` reads `20`; start a fresh TCP connection (a brand-new 4-tuple, not a connection already open before the deploy — the kernel's own in-kernel nf_flowtable entry for a pre-existing connection is not re-created by a module reload and will show 100% `MFLOW_NOT_ACTIVE`/host-fallback forever) and run iperf3 for several minutes. Pass: zero retransmits sustained well past the previous ~75-90s failure window, and the sustained bitrate should exceed the pure host-softpath baseline (~300 Mbit/s) since genuine hardware forwarding is occurring. Fail: `state` still collapses to 0 around the old ~75-90s mark despite the rearm param being active. Result (live, fresh connection, default port, 368s run until user-interrupted): one stall at t=56-59s (the tail of the pre-rearm-deploy behavior / last natural expiry before rearm's first full cycle established the flow), then **zero retransmits for the remaining 308s** (60s->368s) sustaining 367 Mbit/s average (294-325 Mbit/s baseline before), confirming the rearm workaround prevents the deeper firmware expiry bug under sustained active traffic.
